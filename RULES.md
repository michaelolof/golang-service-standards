# Every rule

Generated from the "Rules at a glance" tables. Don't edit it by hand. Each document has the detail, the reasons and examples.

## [01 · Project layout, packages, bootstrap and config](01-project-layout.md)

| ID | Rule |
|---|---|
| LAY-1 | Application code lives in `cmd/` and `internal/`. `pkg/` holds only libraries being incubated for extraction, and they import nothing from `internal/`. |
| LAY-2 | `main` only sets up signals, calls `run(ctx, …) error`, and exits. |
| LAY-3 | One `wire.go` per binary builds every dependency at startup and returns errors. Nothing looks dependencies up at request time. |
| LAY-4 | Long-running components expose `Run(ctx) error` and run under `supervise.Run` (CON-2). |
| LAY-5 | Migrations run only from a command in `cmd/tools/`. Services check the schema version and fail closed. |
| LAY-6 | `internal/` uses one taxonomy: foundation, config, domain, ports, core, repository, adapters, http, workers. |
| LAY-7 | A package imports only the layers its LAY-6 row allows. Each SDK has one home. |
| LAY-8 | The package name equals the directory name. Choose names so importers never need an alias. |
| LAY-9 | Name packages for what they do: never `util`, `helpers`, `common`, `types` or `models`. Place a helper by who uses it. |
| LAY-10 | Name files after their type or use-case. Target ≤ 500 lines; hard limit 1,000. |
| LAY-11 | Every package has a doc comment. No `README.md` under `internal/` or `cmd/`. |
| LAY-12 | Only `internal/config` reads the environment, through an injected lookup. |
| LAY-13 | Config is typed section structs with `Validate()`. Each binary composes its own sections, and each component takes its own small `Config`. |
| LAY-14 | Taskfile has the standard targets. `check` is read-only and is exactly what CI runs. |

## [02 · Style, naming and formatting](02-style-and-naming.md)

| ID | Rule |
|---|---|
| STY-1 | Format with gofumpt and order imports with gci in three groups. Every project uses one shared lint config. |
| STY-2 | Names follow the [naming table](#sty-2--naming). |
| STY-3 | Guard clauses first. Split a function only where a part is its own idea. No length limit; complexity 20, nesting 4, 6 parameters, 3 results. A field tagged `lint:"required"` or `validate:"required"` must be set in every literal. |
| STY-4 | Structs: identity, then data, then timestamps. A named `mu` sits above the fields it guards. Tags in a fixed order, snake_case JSON. |
| STY-5 | Doc-comment every exported identifier. Explain *why*. No step narration, plan references or bare TODOs. |
| STY-6 | Declaration order in a file: consts, vars, type, `New`, exported methods, unexported methods, helpers. |
| STY-7 | Use modern Go: `any`, `range n`, `new(v)`, `slices`/`maps`, `min`/`max`, `wg.Go`. |
| STY-8 | Name policy values and repeated literals. Use stdlib constants for HTTP methods and statuses, except the status in gofi's `c.Send`. |
| STY-9 | A function reads as a story: what it does, in steps, in paragraphs separated by blank lines, with names that say what each value is. |

## [03 · Domain modelling and abstractions](03-domain-and-abstractions.md)

| ID | Rule |
|---|---|
| DOM-1 | Every aggregate identity is a named `[16]byte` type in `domain`, generated by an injected `ids.Generator`. It keeps that type in every layer. |
| DOM-2 | Money is one value type with unexported fields and a validating constructor. |
| DOM-3 | `domain` and `core` never call `time.Now()`. They take `now` or a `clock.Clock`. Times are UTC. |
| DOM-4 | Domain types are used across every boundary. They may carry tags and standard-library driver methods; `domain` imports no driver. |
| DOM-5 | Value objects come from `New…`/`Parse…` returning an error. Entities have `Validate() error`. |
| DOM-6 | Closed sets are enumx types declared one way, with `Parse`, `Validate` and a sorted `Oneof`. |
| DOM-7 | One enum and one transition table per state machine. State changes only via `TransitionTo`. |
| ABS-1 | One interface per dependency per consuming package, declared there, typed only with domain and stdlib types. No interface without a consumer and an implementation. |
| ABS-2 | Implementations assert the interface they satisfy and return concrete types. |
| ABS-3 | Name by role: `-er`, `Store`, domain nouns. Never `I*`, `*Iface`, `*Impl`, `*Adapter` or `*Manager`. |
| ABS-4 | Pure rules are free functions. Orchestration lives in one `Service` per capability. |
| ABS-5 | `New(Deps) (*Service, error)`, validated. No `With*` mutators, exported mutable fields or silent no-op defaults. |
| ABS-6 | One method and one file per use case: `(ctx, XArgs) (XResult, error)`. |
| ABS-7 | One adapter package per SDK. It wraps the SDK once, leaks no SDK types, and translates errors. |
| ABS-8 | Generics only for logic that doesn't depend on `T`. Never type-switch on `T`. |
| ABS-9 | No functional options in services or adapters. No embedded concrete types. Registries are immutable and keyed by enums. |

## [04 · Errors](04-errors.md)

| ID | Rule |
|---|---|
| ERR-1 | Every errx, httperr and log call takes a stamp: the Unix time in milliseconds, as a plain literal, read from a clock. A stamp has no meaning, so it's never ordered, numbered or versioned. |
| ERR-2 | Use only `New`, `Newf`, `NewKind`, `NewKindf`, `Wrap`, `WrapKind` and `IsKind` from errx. For the rest, use stdlib `errors.Is/As/Join`. |
| ERR-3 | Wrap every error you return from a call exactly once with `errx.Wrap(stamp, err)`. |
| ERR-4 | Create errors with `New*`, and add a kind only if someone branches on it. Messages are lowercase, describe the condition, use `key=%q`, and contain no PII. |
| ERR-5 | Application kinds: generic ones in `foundation/errkinds`, capability ones beside their owner with a `<pkg>_` prefix, and only if a caller branches on them. Each transport has its own error domain with its own kinds. |
| ERR-6 | Driver and SDK errors are inspected and translated only in repositories and adapters, with `errors.Is/As` and `errx.WrapKind`. |
| ERR-7 | HTTP handlers return `httperr.Map(stamp, err)`. One mapper, one typed response body. |
| ERR-8 | Each job runtime has one mapping from kind to outcome. Handlers never choose an outcome. |
| ERR-9 | Return an error or log it, never both. Log only at roots. |
| ERR-10 | Discard close errors on readers. Join close errors on writers. Don't `Join` on paths that will be classified. |
| ERR-11 | No `panic` outside tests and `recover` roots. A recovered panic becomes an error with the panic's type and stack. |
| ERR-12 | `fmt.Errorf` and `errors.New` are allowed only in tests and in standalone library modules. |

## [05 · HTTP, background work, context, concurrency, logging and telemetry](05-transport-and-runtime.md)

| ID | Rule |
|---|---|
| HTTP-1 | Handlers follow gofi's [GUIDELINES.md](https://github.com/michaelolof/gofi/blob/v0.10.4/GUIDELINES.md) (v0.10.4): an exported `<Operation>Handler` variable, its schema directly below, dependencies through `deps.MustGet(c)`. |
| HTTP-2 | One operation per file. The package is named after its OpenAPI tag. |
| HTTP-3 | The body follows gofi HND-5. "Do the work" is one call: a service method if the capability has a justified service, otherwise a repository method. No business rules in a handler. |
| HTTP-4 | Schemas use the shared envelopes, and every field has `json`, `validate`, `description` and `example` tags. |
| HTTP-5 | `Info` has one kebab-case tag and a `Description`. No `OperationId`: the method and path identify the route. Lists use `limit` and `cursor` and return `next_cursor`. |
| HTTP-6 | One `routes` package. Global middleware runs in a fixed order; authentication and authorization are mounted per route group. |
| HTTP-7 | `gofi.OpenAPISpec` produces both the live docs and the committed spec, with no post-processing. CI checks for drift. |
| JOB-1 | A job handler is named for one action. `Handle` makes one call (a service method, or a repository method when there is no service) and returns its error. |
| JOB-2 | The runtime adapter owns outcomes: done, retry, drop, dead-letter, defer. One mapping per runtime turns kinds into outcomes; handlers never pick one. |
| JOB-3 | No lost work: record the intent in the same atomic write as the state change, publish after commit as a hint, and sweep for anything recorded but not done. Handlers re-read state and do nothing if the work is already done. |
| JOB-4 | Periodic work is claimed before it runs, and scans only enqueue. Stream consumers commit or ack only after a durable outcome, and dead-letter with a replay path. |
| CTX-1 | A ctx carries cancellation, deadlines, the trace, log attributes and adapter-private handles. Nothing else. |
| CTX-2 | Context keys are unexported `struct{}` types, accessed through `WithX` and `XFrom`. Never mutate a ctx. |
| CTX-3 | Handlers use gofi's request context, `c.Context()`. Middleware replaces it only through `gofi.SetRequestContext`. Every request gets a deadline from `gofimw.ContextTimeout`. |
| CTX-4 | `context.Background` and `TODO` appear only in `main`, `run` and tests. Detached work uses `context.WithoutCancel` plus a timeout. |
| CON-1 | Every goroutine has an owner that waits for it, using `errgroup` with `SetLimit`. |
| CON-2 | Each long-lived loop is its own `Run(ctx)` component under `supervise.Run`. No `time.Sleep`. Work requested by a request or by core is a durable job, never a `go` statement. |
| CON-3 | Both ends of a pipe run in one errgroup, and each side closes the pipe with its error. |
| LOG-1 | One process-wide logger, called as `logger.Info(stamp, ctx, event, key, value, …)`. Nothing injects a logger; nothing else calls `slog`. |
| LOG-2 | Keys are snake_case string literals. An error goes under `error` as the error value. |
| LOG-3 | The event name is a constant, dotted name in the past tense. The stamp says where; the event name says what. |
| LOG-4 | Levels have fixed meanings. Secrets are redacted at the type level and by the handler. |
| OBS-1 | Telemetry is set up once. Instrumentation lives at the edges: HTTP middleware, the job runtime, and contrib clients in adapters. |
| OBS-2 | Metric names are OTel-style and dotted, with UCUM units and bounded attributes. |
| OBS-3 | A capability with metrics declares its own typed `Metrics` struct, built from an injected `metric.Meter`. |

## [06 · Persistence and data access](06-persistence.md)

| ID | Rule |
|---|---|
| DATA-1 | One package per aggregate, with a fixed set of files: `repo.go`, `row.go`, and one file per use case. |
| DATA-2 | Repository methods take and return domain types. A database schema type isn't a domain type: it's private to the repository, and its fields may use domain types. One column list and one scan function per table, in `row.go`. |
| DATA-3 | Method verbs come from a closed set, and names don't repeat the package name. |
| DATA-4 | A change to several rows is one repository method named for the use case. Prefer one atomic statement (a CTE); otherwise the repository owns the transaction. Core never holds database semantics. |
| DATA-5 | Every query is a constant, declared inside the method that runs it. It moves to package level only when several methods share it. |
| DATA-6 | Time comes from the clock. SQL `now()` is never used. |
| DATA-7 | Optimistic concurrency uses a version column with an atomic compare-and-set. A CAS is never read-then-write. |
| DATA-8 | Idempotency keys are unique per tenant in the primary store. `CreateOrGet` returns `created bool`. |
| DATA-9 | One `pagination` package handles keyset cursors with a tie-breaker and a filter fingerprint. Driver page tokens never leave the repository. |
| DATA-10 | A cache is a decorator that implements the same port as the repository. Redis code is split into one package per role, and keys follow a fixed format. |
| DATA-11 | Migrations are timestamped, forward-only and safe to re-run, live in `db/migrations`, and run only from the migrate tool. |
| DATA-12 | Split large files by aggregate, then by concern. |

## [07 · Testing](07-testing.md)

| ID | Rule |
|---|---|
| TEST-1 | Each kind of test has one home and one build tag. A test with no tag uses no infrastructure. Each behaviour is tested once, at the lowest layer where it is real. |
| TEST-2 | Under its tag, missing infrastructure fails the test; it never skips. Nothing is gated by `testing.Short()` or environment variables. |
| TEST-3 | Run one docker-compose stack through Task, and isolate tests by namespace. Never reset or flush global state. |
| TEST-4 | Use testify `require` only, and compare whole values. |
| TEST-5 | Test doubles are hand-written fakes named `fake…`. They are small working implementations that never embed the interface. |
| TEST-6 | A shared fake lives in `xtest` and passes the same conformance suite as the real adapter. |
| TEST-7 | Tables are for three or more data-only cases. Rows hold no functions and the loop body has no branches. Names follow fixed patterns. |
| TEST-8 | `t.Parallel()` is optional. Use it where a test shares nothing. |
| TEST-9 | Helpers take `t testing.TB`, call `t.Helper()`, fail with `require`, use `t.Context()` and register `t.Cleanup`. |
| TEST-10 | Builders return valid values with fixed IDs and times. `testdata/` holds no Go code. |
| TEST-11 | Each layer has one testing recipe. |
| TEST-12 | Time, IDs and randomness are injected. Use `synctest` inside a process. Polling across processes must fail on timeout. |
| TEST-13 | Architecture tests are table-driven, typed, and check that they inspected something. |
| TEST-14 | Restructuring tests is paused. Existing tests stay as they are during refactors, as the guardrails. |

## [08 · Security](08-security.md)

| ID | Rule |
|---|---|
| SEC-1 | API keys have at least 256 random bits, are stored as a peppered HMAC, and are checked for status and expiry on every request. A cached auth result lives at most 60 s and is evicted on revoke. |
| SEC-2 | Access tokens are short-lived and fully validated. Refresh tokens are opaque, stored hashed, rotated on use, and revocable. Session tokens never appear in URLs. |
| SEC-3 | Passwords use Argon2id through one package. Login takes the same time for unknown users, and is rate-limited before authentication in a shared store. |
| SEC-4 | OAuth and OIDC flows use PKCE, and state that's single-use, short-lived and bound to the browser, user and resource. Verifiers and client secrets stay on the server. JWKS and token responses are size-bounded. |
| SEC-5 | Tenant and org come only from the principal. Middleware checks the parent resource in the URL first. Tenant-data repository methods take a typed scope; an empty scope is an error, never "all". |
| SEC-6 | Permissions are deny-by-default, checked per route group, and denials are audited. Config, secrets, members and roles need the right role, not just membership. |
| SEC-7 | Secrets are loaded once, into a type that redacts itself. Outside development, config validation rejects dev defaults, dev-only adapters and disabled TLS checks. |
| SEC-8 | Never log tokens, links that contain tokens, request bodies, or personal data. Log IDs. |
| SEC-9 | Encryption at rest is AEAD through one helper: random nonce, AAD that binds the ciphertext to its owner, versioned envelope, KMS data keys. |
| SEC-10 | Webhook signatures are HMAC-SHA256 over timestamp and body, verified in constant time within a ±5 min window. A missing secret is a failure, never a skip. |
| SEC-11 | `crypto/rand` for anything an attacker could guess. `math/rand/v2` only for jitter. |
| SEC-12 | Every server and upload route sets a body limit. Uploads check size and sniffed type. |
| SEC-13 | Customer-supplied URLs go through the shared SSRF client. Every HTTP client has a timeout, a bounded body read, and no redirects unless needed. |
| SEC-14 | TLS verification is never switched off in production. |
| SEC-15 | Values are bound as parameters. Identifiers come from code. JSON, SQL, CQL and Lua are never built with `fmt`. |
| SEC-16 | Clients see only messages written for clients. Authentication failures get one generic message. |
| SEC-17 | Every server sends security headers, names its CORS origins, and sets read, write and idle timeouts and a connection limit. |
| SEC-18 | `govulncheck` blocks CI. The Go patch version is pinned. Test infrastructure never ships in production packages. |
| SEC-19 | Every ID in a path, body or payload is checked against the caller. Another tenant's object gets the same answer as a missing one. |
| SEC-20 | Each kind of token does one job, and every parser checks the kind. Halfway through sign-in, the caller can only finish signing in. Sensitive actions ask for verification again. |
| SEC-21 | Invitations need the invited, verified email. OAuth links to an existing account only on a verified provider email. Claims and redemptions are atomic. |
| SEC-22 | Typed request bodies list what a client may edit. Server-owned fields are never read from client JSON. |
| SEC-23 | Identifiers that route inbound traffic are unique across tenants, proven with the provider, and enforced with a partial unique index. |
| SEC-24 | Capability tokens and links are bound to their tenant and resource, expire, and are redeemed atomically when single-use. |
| SEC-25 | Secrets stay out of URL errors, comparisons are constant-time, and GET endpoints don't return secrets to roles that don't need them. |
| SEC-26 | Security audits follow `security-audit.md`: read-only until findings are approved, and a finding counts only once it's proven. |

## [09 · Collaboration: how engineers and agents work on a task](09-collaboration.md)

| ID | Rule |
|---|---|
| COL-1 | Instructions are applied in a fixed priority order. General best practice never overrides the standard. |
| COL-2 | Every task starts with a brief that says what "done" means. |
| COL-3 | The agent reads before it writes, then lists ambiguities and proposed cases. The engineer resolves them. |
| COL-4 | Acceptance tests come first, and the implementer is never their only author. |
| COL-5 | Task-list work, and any work that adds a package, type, interface, service or table, starts with a plan the engineer approves. |
| COL-6 | Implement in small steps, each ending green. Change only what the task needs. |
| COL-7 | Refine against the standard with tests green, then run `task check`. |
| COL-8 | Report in binary terms: done or not done, with the evidence. Never "should work". |
| COL-9 | Explain until the engineer understands the change. Understanding is part of done. |
| COL-10 | Review covers four concerns: works, solves the real problem, fits, reads well. |
| COL-11 | Stop rules: two failed attempts, growing scope, a request that breaks the standard, or pressure to skip a step. |
| COL-12 | Autonomy is granted per task type and earned through measured results. |
| COL-13 | Every repeated correction becomes a rule, a check, or a canonical example. |
| COL-14 | Everything written for a person uses clear, approachable language, with a practical example and a code source. |
| COL-15 | Each project keeps one living `tasklist.md`: a tracker table grouped into phases that each deliver something useful, linked to a section per task. |
| COL-16 | Each task being worked on is detailed in a short-lived implementation plan in `implementation/`, which ends when its tasks do. |

## [10 · Adoption: how a project takes on this standard](10-adoption.md)

| ID | Rule |
|---|---|
| ADO-1 | The standard is a git repo with version tags. A project adds it at `.standards/` with `git subtree`, and pins the version. |
| ADO-2 | Nobody edits `.standards/` inside a project. |
| ADO-3 | Each code repo has one `AGENTS.md` at its root, which says the rules are mandatory and loads the rule index. A subfolder may add its own. |
| ADO-4 | An agent can't finish its turn, or push, while the checks fail. |
| ADO-5 | `task check` runs every check, and it's a required check on the default branch. |
| ADO-6 | An existing project fixes everything first, and its existing tests stay as they are. |
| ADO-7 | A rule changes through a PR on the standard, approved by its owner. Projects upgrade with a normal PR. |
